# 轮电机反馈缺失与双中启动报错

实车运行 `wheel-leg-infantry-wheelbipe-recovery` 时，双中触发
`invalid command, calibration or feedback`。只读查询实际运行进程的
`/rmcs/service/robot_status` 得到：

- 四个 DM 腿电机反馈年龄约 3–9 ms，`dm feedback fresh: 1`。
- IMU 反馈年龄约 0.36 ms。
- 两只轮电机均为 `feedback_age_ms=-1`，表示本次进程尚未解码到匹配的轮反馈。
- 整体 `feedback fresh: 0`。安装配置及策略日志均指向
  `wheelbipe_v202_8500_50hz.onnx`。

缺失任意轮反馈会使整体反馈门关闭；控制器随后锁存故障并保持零输出。
这些读数定位到轮电机接收路径，尚不能区分接线、供电、电调 ID、板卡通道或上报问题。

原实现先检查整体 `feedback_fresh`，再计算各轴接收诊断，因此故障日志中的
`mask=0xff` 和三个 `age=-1` 可能只是未更新的默认值，不能据此判断所有传感器断线。
现在先更新接收诊断，再应用原有反馈门。只有两轮缺失、四腿和 IMU 正常时，
P 顺序的无效位应为 `0x30`（bit 4/5）。反馈缺失时仍禁止使能与非零输出。

## 当前硬件映射

| SDK 通道 | 设备 | 电机 ID | 接收帧 ID | 命令帧 ID |
| --- | --- | --- | --- | --- |
| `kCan0` | 左/右 M3508 轮电机 | 1 / 2 | `0x201` / `0x202` | `0x200`，前两个 16 位槽 |
| `kCan1` | 左/右 DM 髋电机 | 1 / 2 | YAML `dm_master_ids` 前两项 | 1 / 2 |
| `kCan2` | 左/右 DM 膝电机 | 1 / 2 | YAML `dm_master_ids` 后两项 | 1 / 2 |

轮电机沿用原硬件代码的通道、ID、反转和 15.62 减速比。
`kCan0` 是 SDK 名称；必须对照实物板卡的端口标记，不能凭一基/零基编号猜接线。
当前轮反馈仅接受标准 CAN 数据帧且长度为 8 字节。

## 只读诊断

在已配置机器人 SSH 的开发容器中运行：

```bash
.script/remote-status
```

也可以在机器人已加载 ROS 环境的终端调用：

```bash
ros2 service call /rmcs/service/robot_status std_srvs/srv/Trigger '{}'
```

硬件状态新增四路 `CAN[kCanN]` 行：`rx` 为收到的回调数，`matched` 为匹配到
该通道电机的帧数，`rejected` 为扩展帧、远程帧或长度不为 8 的帧数。
同时显示最近 ID、长度、接收年龄及本进程见过的标准帧 ID（最多列出 16 个）。

比较连续两次状态查询：

| 读数 | 下一步定位 |
| --- | --- |
| `kCan0 rx=0` | 主机尚未收到该通道回调；检查实际端口、轮电调供电、CAN 线路及板卡上报 |
| `kCan0 rx` 增长但 `matched=0` | 对照实际 ID 和帧长度；`0x203/0x204` 等不会匹配目前的 1/2 号轮电机 |
| 其他通道出现 `0x201/0x202` | 核对轮电机实际接入通道 |
| `matched` 增长但轮反馈时间仍为 `-1` | 检查接收快照到 executor 发布的路径 |

计数和 ID 集合从进程启动累计，不因双下归零；其接收年龄用于区分历史流量与当前流量。
`0x200` 命令提交时间只证明主机向 SDK 排队，不能证明板卡已在 CAN 总线上发送成功，
也不能证明电调收到命令。诊断不改变控制保护、CAN 映射或策略。
